01ACCOUNT

注册并保护 GitHub 账号

GitHub 是项目的线上保险箱；Repository（仓库）是一个项目的文件与历史；GitHub Pages 会把仓库里的静态网站发布成公开网址。免费个人账号足够完成本教程。

你亲手完成注册、邮箱验证和设置密码。
Codex 可以帮助解释公开错误和按钮含义，但绝不能接收密码或验证码。

1.1 创建免费个人账号

1
打开注册页
github.com/signup。准备一个长期可访问的邮箱。
2
设置密码和用户名
用户名会公开显示，也可能进入默认网址 YOUR_USERNAME.github.io。建议简短、易拼写、不含真实证件号码。
3
完成人机验证和邮箱验证
到邮箱打开 GitHub 发来的验证链接。没有验证邮箱时，创建仓库等基本功能可能受限。
4
重新登录做一次确认
确保密码管理器已保存正确账号，并能打开 github.com/new。
基础安全提醒：密码、邮箱验证码、身份证件和支付信息都不要发给 Codex。Codex 可以解释页面和错误，但不需要这些秘密。

03WORKSPACE

先给项目创建一个安全的本地文件夹

这是正式建站前的必需步骤。工作文件夹就是 Codex 的工作边界：一个项目一个文件夹，不要把整个桌面、下载目录或用户主目录交给 Codex。

你亲手完成在 Finder/文件资源管理器创建文件夹，并在 Codex 中选择它；启动 Codex 前必须先有安全边界。
之后交给 Codex只读确认路径与目录内容，并在这个文件夹内初始化项目。

3.1 推荐命名

  • 小写英文字母、数字和短横线，例如 my-personal-site。
  • 初学者尽量避开空格、中文、特殊符号和网盘同步目录，减少路径与权限问题。
  • 本教程示例：macOS 使用 ~/Projects/my-personal-site；Windows 使用 C:\Users\你的用户名\Projects\my-personal-site。

3.2 macOS 创建并进入目录

Terminal
mkdir -p ~/Projects/my-personal-site
cd ~/Projects/my-personal-site
pwd
ls -la

mkdir 创建文件夹，cd 进入文件夹，pwd 显示绝对路径，ls -la 显示目录内容。

3.3 Windows PowerShell 对照

PowerShell
New-Item -ItemType Directory -Force "$HOME\Projects\my-personal-site"
Set-Location "$HOME\Projects\my-personal-site"
Get-Location
Get-ChildItem -Force
暂停检查：屏幕上的路径必须以 my-personal-site 结尾。目录应为空，或只包含你明确放入的本项目文件。如果看到大量私人文件，立刻停止并进入正确目录。

3.4 让 Codex 先只读确认工作区

在 Codex 中选择这个文件夹作为 workspace，然后复制下面的提示词。

第一次交给 Codex 的安全提示词
当前工作目录应当是我的个人网站项目目录。
请先只读检查当前路径和目录内容，告诉我：
1. 当前绝对路径；
2. 目录里已有的文件；
3. 是否适合初始化一个新的网站项目。
在我确认前，不要删除、移动或覆盖任何文件，也不要访问父目录。
成功标志：Codex 报告的路径与你刚创建的路径一致；没有其他项目或私人资料；后续命令都在这个目录执行。
04BRIEF

Codex 最怕的不是需求少，而是目标含糊。先定义谁来看、看完做什么、必须展示什么，再谈颜色和动画。

你亲手完成决定网站目标、哪些内容可以公开，并在重要方案中做选择。
交给 Codex主持访谈、整理设计简报、给出方案和成功标准。

目标与受众

客户、招聘方、朋友，还是产品用户？首要行动是体验、联系还是阅读？

内容与素材

产品名称、介绍、截图、头像、文章、邮箱；哪些可公开，哪些必须脱敏？

技术与上线

05BUILD

用 Codex 创建 Astro 静态网站

主线使用 Astro + TypeScript + Markdown Content Collections + 原生 CSS。你不必先学会所有代码，但必须知道每类文件在哪里、Codex 改了什么、怎样验证。

你亲手完成确认 Codex 总结的设计方案和将要创建的文件。
全部交给 Codex初始化 Astro、安装依赖、创建页面组件、写样式并运行验证。

推荐：Astro 项目

适合多个产品、文章、多语言和长期更新。构建后发布 dist/。

快捷：单个 index.html

适合一次性简单页面。无需构建，但内容增长后维护困难。本教程不把它作为主线。

5.1 初始化前让 Codex 说明动作

实施提示词
PLEASE IMPLEMENT THIS PLAN。

请在当前空项目目录创建 Astro + TypeScript 纯静态网站：
- 内容使用 Markdown Content Collections；
- 样式使用原生 CSS，不引入 UI 框架；
- 输出目录为 dist；
- 手机和桌面均可用；
- 不依赖后端、数据库或登录；
- 不写入项目目录之外；
- 不覆盖我没有授权修改的文件。

开始前先告诉我：
1. 将创建的主要文件；
2. 将执行的安装命令；
3. 完成后运行哪些最小验证。
然后直接实施、构建并汇报真实结果。

5.2 认识项目地图

位置作用初学者要知道什么
src/pages/每个页面的入口index.astro 通常是首页
src/components/导航、产品卡、页脚等复用部件相同结构不要复制多份
src/content/产品或文章 Markdown内容和页面结构分开维护
public/公开图片与静态文件放进去的内容可能被任何访客访问
package.json依赖和运行命令使用 npm 脚本，不随意手改版本
dist/构建后的可部署成品它由构建生成，不是主要编辑区

5.3 每次修改都使用“小任务”

局部修改模板
请在不改变现有技术栈和其他页面的前提下，完成这个小任务：
【写清楚一个具体变化】

验收标准：
- 【访客能看到或完成什么】
- 【桌面与手机如何表现】
- 【必须保留什么】

不要这样说：“帮我把网站改高级一点”。改为说清楚对象、受众、问题、期望结果和不允许改变的部分。

07VERSION CONTROL

用 Git 保存历史，再连接 GitHub

本地文件夹是工作现场；本地 Git 仓库记录版本；GitHub 远端仓库保存可同步的副本。三者不是同一个东西。

你亲手完成第一次登录 GitHub、批准创建公开仓库，以及把 SSH 公钥添加到账户。
优先交给 Codex检查隐私、初始化 Git、提交、用 SSH 创建/连接远端并推送。

7.1 优先让 Codex 创建并推送仓库

复制给 Codex：创建 Git 与 GitHub 仓库
请替我完成当前网站的 Git 和 GitHub 初始化，但外部创建前先向我确认一次。
要求：
- 先检查 .gitignore 和敏感信息，发现密码、API Key、证件、手机号或原始简历就停止；
- 运行相关最小构建，确认项目可用；
- 初始化 Git，提交当前项目，主分支使用 main；
- 检查 gh auth status；如果 GitHub CLI 已登录，在我确认后创建公开仓库 YOUR_REPO；
- GitHub 远端必须使用 SSH：git@github.com:YOUR_USERNAME/YOUR_REPO.git；
- 推送后验证远端和 git status；
- 不使用 reset --hard，不删除文件，不改成 HTTPS 远端。
如果缺少登录或 SSH Key，请停在那一步，给我官方网址和我必须亲手完成的具体操作。

7.2 如果 Codex 提示必须手动创建

打开 https://github.com/new：Owner 选择你的账号；Repository name 填与本地文件夹一致的名称；选择 Public；不要勾选自动添加 README、.gitignore 或 License；点击 Create repository。然后回到 Codex，告诉它“空仓库已创建，请继续使用 SSH 推送”。

7.3 Codex 检查隐私和 .gitignore

提交前让 Codex 检查是否包含 .env、API Key、原始简历、手机号、证件、客户内部文件和系统缓存。公开网站所需邮箱可以保留，但必须是你明确允许公开的邮箱。

08DEPLOY

用 GitHub Pages 自动发布

源代码不能直接当成 Astro 网站发布。GitHub Actions 会安装依赖、运行构建、上传 dist/，再把它部署到 Pages。

你亲手完成在 GitHub Settings → Pages 中确认 Source 为 GitHub Actions，并打开部署网址验收。
交给 Codex创建工作流、调整 Astro 路径、构建、提交推送并读取 Actions 结果。
复制给 Codex：完成 GitHub Pages 部署
请替我把当前 Astro 静态网站部署到 GitHub Pages：
1. 检查现有 package.json、astro.config.mjs、构建输出和 Git 远端；
2. 使用当前 GitHub Pages 官方 Actions 创建 .github/workflows/deploy.yml；
3. 上传 npm run build 生成的 dist，不要发布源码目录；
4. 根据“默认 github.io 项目网址 / 自定义域名”正确处理 site 和 base，不要盲改当前单文件内联方案；
5. 本地构建通过后展示 diff；
6. 经我确认后提交并推送；
7. 如果能读取 Actions，等待结果并告诉我部署网址；否则告诉我在 GitHub 哪个页面查看。
不要购买服务，不要修改 DNS。

8.1 先设置 Pages 来源

打开 https://github.com/YOUR_USERNAME/YOUR_REPO/settings/pages（先替换用户名和仓库名），或在仓库依次点击 Settings → 左侧 Pages → Build and deployment → Source 选择 GitHub Actions。如果已经显示 GitHub Actions，就不要重复修改。

8.2 创建工作流

请 Codex 创建 .github/workflows/deploy.yml。下面版本采用 GitHub 当前官方 Pages Actions；未来版本更新时以官方文档为准。

.github/workflows/deploy.yml
name: Deploy to GitHub Pages

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: true

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v6
      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - name: Install
        run: npm ci
      - name: Build
        run: npm run build
      - name: Configure Pages
        uses: actions/configure-pages@v5
      - name: Upload dist
        uses: actions/upload-pages-artifact@v4
        with:
          path: ./dist

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - name: Deploy
        id: deployment
        uses: actions/deploy-pages@v4

09DOMAIN

在阿里云申请和购买域名

域名是网站地址，不是服务器。你可以在阿里云购买域名，却把网站托管在 GitHub Pages。域名价格、优惠和可注册状态以结算页为准。

必须亲手完成阿里云登录、实名认证、证件提交、选择订单、付款和续费设置。
Codex 可以帮助比较候选域名、解释字段和检查公开信息；不能代替你实名或付款。

9.1 先准备持有者信息模板

先打开 阿里云登录页。登录后进入 域名控制台，找到 信息模板，选择个人或企业主体，按真实证件填写持有者资料并等待审核。域名持有者名称应与你未来可能使用的备案主体保持一致。证件只提交给阿里云官方页面，不交给 Codex。

9.2 查询和选择域名

1
打开 wanwang.aliyun.com/domain，输入候选名称并查询。
2
优先选择短、易拼写、口头能说清的域名；检查续费价格，不只看首年活动价。
3
确认没有侵犯他人商标、姓名或组织权益；不要用敏感个人号码做域名。
4
选择已实名的信息模板、注册年限并核对订单。支付是外部真实交易，最终提交前由你亲自确认。
5
购买后进入域名控制台，确认状态正常、实名认证完成，并开启续费提醒。

10DNS + HTTPS

连接自定义域名、配置 DNS 和 HTTPS

顺序很重要：先让 GitHub Pages 认领自定义域名，再在阿里云 DNS 把访问者指向 GitHub。DNS 不是网页跳转，它像互联网通讯录。

你亲手完成在 GitHub Pages 保存域名、在阿里云控制台新增 DNS 记录、最后开启 HTTPS。
交给 Codex根据你的公开域名准备记录表、运行 dig/Resolve-DnsName、判断传播和冲突。

10.1 在 GitHub Pages 添加域名

打开 https://github.com/YOUR_USERNAME/YOUR_REPO/settings/pages，找到 Custom domain，填写 YOUR_DOMAIN，点击 Save。使用自定义 Actions 发布时，GitHub 官方说明不要求依赖仓库中的 CNAME 文件；以 Pages 设置中的域名为准。

10.2 在阿里云添加根域名 A 记录

打开 https://dns.console.aliyun.com/ → 公网权威解析 → 找到域名 → 解析设置 → 添加记录。为主机记录 @ 分别添加以下四条 A 记录。解析请求来源选择“默认”，TTL 使用默认值或 10 分钟。

记录类型主机记录记录值
A@185.199.108.153
A@185.199.109.153
A@185.199.110.153
A@185.199.111.153

10.3 添加 www CNAME

记录类型主机记录记录值
CNAMEwwwYOUR_USERNAME.github.io
不要添加不必要的 * 通配符记录。如果已经存在相同主机记录的 A、CNAME 或 URL 转发，先确认用途；冲突记录不要同时保留。

10.4 验证 DNS

macOS / Linux
dig YOUR_DOMAIN +noall +answer -t A
dig www.YOUR_DOMAIN +noall +answer -t CNAME
Windows PowerShell
Resolve-DnsName YOUR_DOMAIN -Type A
Resolve-DnsName www.YOUR_DOMAIN -Type CNAME

新记录可能很快生效，修改旧记录通常至少需要等待原 TTL，全球传播最长可能到 24 小时。不要在等待期间连续删除重建。

10.5 开启 HTTPS

GitHub Pages 检测 DNS 后会申请证书。等 Settings → Pages 中 Enforce HTTPS 可选时勾选。随后验证：

11COMPLIANCE

域名实名、ICP备案与访问说明

购买域名不等于完成备案；是否需要 ICP 备案主要取决于网站实际接入的服务器地域，而不是域名在哪里买。

你亲手完成确认真实业务、服务器地域和所在地要求；需要备案时只在官方平台提交。
交给 Codex扫描网站公开内容与仓库敏感信息，并列出需要你确认的风险，不替代法律判断。
复制给 Codex：上线前隐私与公开内容检查
请对当前静态网站和即将提交的文件做只读上线检查：
- 查找密码、API Key、.env、证件号、手机号、家庭地址、原始简历、客户内部资料和本机绝对路径；
- 区分“必须删除”“需要我确认”“允许公开”；
- 检查图片、链接、表单、统计脚本和第三方资源；
- 不打印任何秘密的完整值，只报告文件路径、问题类型和安全的脱敏片段；
- 不删除文件，等我确认后再修复。
备案和法律问题只列出需要向实际接入商或主管部门核实的事项，不给确定法律结论。

当前主线：GitHub Pages

GitHub Pages 不属于中国内地服务器。按阿里云当前说明，解析到非中国内地服务器不需要通过阿里云办理 ICP 备案。

未来迁入中国内地服务器

需要在实际接入服务商处按要求完成 ICP 备案后再开通网站；备案主体、域名实名和服务器资格需匹配。

重要边界：这是一份建站教程，不是法律意见。政策和地区要求会变化；如果网站长期面向中国大陆公众、涉及收费、论坛、医疗、教育、金融等内容，应咨询实际接入商和主管部门。

中国大陆访问体验

GitHub Pages 的中国大陆访问速度、稳定性和资源可达性需要用真实设备与网络测试，本教程不作保证。不要因为自己电脑能打开，就宣布所有访客都能稳定访问。

上线前内容合规与隐私检查

  • 只发布拥有权利或已获授权的文字、图片、字体和截图。
  • 公开简历另做脱敏版；不要上传手机号、家庭地址、身份证、合同和客户内部资料。
  • 说明产品当前状态，不伪造用户数、收入、客户 Logo 或功能。
  • 若收集表单、分析数据或 Cookie，补充隐私说明；纯静态站能不收集就不收集。

核对官方来源

  • 阿里云：备案前的服务器及接入信息确认
  • 阿里云：域名实名认证、备案和账号实名认证的区别

12MAINTAIN

持续更新网站，并让 Codex 真正解决问题

上线不是终点。可靠的循环是：回到正确目录、检查状态、做一个小改动、本地验证、提交推送、观察部署、线上复验。

进入项目→git status→让 Codex 修改→本地验证→检查 diff→commit / push→Actions→线上复验

高质量排错提示词的 6 个证据

  1. 操作系统和工具版本。
  2. 当前目录。
  3. 刚执行的完整命令。
  4. 完整错误原文，不只截最后一行。
  5. 预期结果和实际结果。
  6. 已经尝试过什么，以及每次结果。
